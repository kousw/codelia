CODELIA · ARCHITECTURE

Codelia Architecture

Codelia consists of a TypeScript agent SDK (core), the host that actually drives it (runtime), and a Rust terminal UI (crates/tui). Three ideas capture the whole design:

  1. Three processesThe CLI launches the TUI, and the TUI spawns the runtime. The TUI and runtime talk exclusively over stdio JSON-RPC.
  2. Boundary logic lives in runtimeTools, permissions, sandboxing, auth, and sessions belong to runtime. core performs no I/O of its own.
  3. The agent is a for-loopCall the LLM → execute returned tool_calls → append results to history, repeating until no tool_calls remain.

Overview: processes and boundaries

When a user runs codelia in a terminal, the Node CLI locates the OS-specific TUI binary and launches it, and the TUI spawns runtime as a child process. Only runtime touches LLM APIs, MCP servers, the OS shell, and local disk storage. The TUI stays focused on screen rendering and user input.

Tracing a single run

As a concrete example, follow what happens when a user asks in the TUI: “Find why this test fails and fix it.” The flow includes the LLM calling a read tool first, then asking the user for confirmation before editing or executing a protected action.

Dependency invariants

  • protocol must not depend on core; wire types live in protocol or shared-types.
  • Add new RPC methods in catalog.ts as Zod schemas — never hand-write duplicate TS/Rust method types or JSON strings.
  • shared-types has zero workspace dependencies.
  • cli must never call core directly; route through runtime.
  • Built-in tools and sandboxing belong exclusively to runtime, never leaking back into core tool contracts.

protocol / shared-types

packages/protocol · packages/shared-typesWire contract · Single source

TakeawayThe sole definition of every message spoken between a UI client and the runtime. All methods are declared as Zod schemas in catalog.ts, which drives TypeScript types, runtime validation, and the generated Rust crate crates/protocol.

Four channels
UI → runtime requests (run.start, run.cancel, session.open, model.set, …), UI → runtime notices (ui.context.update), runtime → UI notices (agent.event, run.status, run.metrics, run.summary), runtime → UI requests (ui.confirm.request, ui.pick.request, client.tool.call)
Runtime order
Unknown-method check → capability/state gates → Zod safeParse → handler. Failures return INVALID_PARAMS without echoing invalid values. UI responses are likewise validated via parseUiResult.
Rust crate
crates/protocol (codelia-protocol, Rust 1.93.1+). Pairs generated generated.rs with hand-written lib.rs (IncomingMessage::classify, request_line, etc.). Malformed known methods surface as DecodeError diagnostics without crashing subsequent messages; Unknown is reserved for unrecognized methods and tag values.
Negotiation
initialize advertises client capabilities (e.g., supports_text_delta opts into streaming text/reasoning deltas); unadvertised channels stay silent.
Dependencies
protocol → shared-types, zod. shared-types has zero workspace dependencies (zod only).
Specs
ui-protocol.md · protocol-codegen.md · methods.md (generated method table)

storage

packages/storageIntegration

TakeawayAll concrete local persistence: layout resolution (~/.codelia/ by default), conversation history and session index, run logs, credentials, and caches for tool output, images, attachments, and tasks. runtime binds through core interfaces so embedded hosts can swap backends.

On-disk layout

The default is a single home layout under ~/.codelia/. Setting CODELIA_LAYOUT=xdg splits config into ~/.config/codelia/, caches into ~/.cache/codelia/, and sessions/logs into ~/.local/state/codelia/ (respecting XDG_*_HOME). All path resolution goes through resolveStoragePaths() in paths.ts.

Three-layer conversation persistence

Each session splits persistence across three files with distinct roles so compaction never destroys history while resume stays fast.

LayerLocationContents & guaranteesOwner
Journalsessions/messages/Accepted user / assistant / reasoning / tool records appended line by line. Never rewritten on compaction; writes are awaited before calling the Agent.session-state.ts · conversation-archive.ts
Active contextsessions/contexts/Messages sent on the next LLM call plus the byte offset covered in the journal; strips ephemeral startup system prompts.SessionStateStoreImpl
Indexsessions/state.dbMetadata for session listing/resume pickers, session → run-log mapping, goals, and applied Steer approval evidence.session-state.ts · session-run-index.ts · session-goals.ts

The journal is searchable inside the same session via conversation_search and conversation_read. Record IDs correspond to stable byte offsets, and truncated tail lines fail cleanly.

Run logs and usage logs

  • Each run writes one JSONL record per event (header, run.start, agent.event, llm.usage, run.end) to sessions/YYYY/MM/DD/<run_id>.jsonl via SessionStoreWriterImpl and RunEventStoreFactoryImpl.
  • Normal logs omit full raw LLM payloads and raw tool outputs; full diagnostic dumps are written separately under sessions/diagnostics/ only when CODELIA_DEBUG=session-dump is set explicitly.
  • Token usage is mirrored independently under usage/ so cost/token aggregation survives run-log compression.
  • Startup retention (run-log-retention.ts) compacts unpinned run logs older than 30 days (or on archive) to .jsonl.gz, dropping heavy diagnostic records while preserving conversation and lifecycle events. Journals, active contexts, state.db, tasks, and usage logs are untouched.
  • Active writers register PID + process-identity markers in active-runs/ so retention skips in-flight logs.

Credentials

  • Backend selection follows auth.storage (auto | keyring | file, overridable via CODELIA_AUTH_STORAGE). On macOS, auto/keyring uses Keychain (codelia.auth / codelia.mcp-auth); elsewhere credentials live in credentials/*.json.
  • File writes stage into a same-directory temp file with mode 0600, fsync, and atomic rename (atomic-file.ts); Windows validates owner/SYSTEM ACLs (windows-acl.ts).
  • Concurrent updates from CLI and runtime serialize through SQLite BEGIN IMMEDIATE locks in auth-lock.ts (35 s wait budget).
  • Switching backends or migrating legacy root auth.json files records intent in storage-state.json first so interrupted migrations never leave split brains (credential-backend.ts · credential-migration.ts).
  • MCP tokens bind to connection metadata (resource_uri, issuer, token endpoint, client_id); unbound legacy entries are discarded so users re-authenticate safely (mcp-auth-store.ts).

Connection with runtime

At startup, runtime inspects environment.adapters.stores and uses supplied adapters when embedded or falls back to concrete storage implementations. Under persistence.mode = "volatile", everything switches to in-memory stores with zero disk writes.

cli

packages/cliApp

TakeawayThe product entrypoint — thin by rule, with zero agent or tool logic. It locates and spawns the OS-appropriate TUI binary and exposes management subcommands (auth, mcp, session, update).

Key files
tui/launcher.ts (resolves @codelia/tui-<os>-<arch>) · commands/ · update/ (self-update)
Handoff to TUI
Passes CLI version, bundled runtime command, update notice, and startup confirmations via a single --internal-launch-context=<json> argument — never env vars — so internal metadata cannot leak into shells or subagents.
Priority rule
TUI implementation takes priority over temporary CLI workarounds.

crates/tui

crates/tui · Rust (ratatui + crossterm)Primary UI

TakeawayFollows a pragmatic TEA (The Elm Architecture) loop over AppState. Runtime messages, terminal events, and local task completions enter as typed Msg variants, update mutates state, and side effects leave cleanly as RuntimeTx writes and returned Effect values — without re-implementing runtime domain policy.

Startup
main.rs (wiring) → entry/ (cli.rs arg parse, launch_context.rs CLI handoff, terminal.rs raw mode) → entry/run_loop.rs
State pillars
PendingRpcs: unified in-flight RPC map (one slot per kind; Steer allows multiple). OverlayState: three-tier overlay model (RuntimeDialogs with independent confirm/prompt/pick slots, local panels, queue/steer pickers). PasteTarget: single routing decision for pasted input.
Module layering
entry → event_loop → app; inside app, handlers / view / render / runtime → state one-way. Import guards in main_tests.rs catch boundary violations.
Wire types
Consumes crates/protocol (codelia-protocol) via path dependency using send_request::<methods::X> and decode_result::<methods::X>; decode failures emit a diagnostic line cleanly.
Client tools
TUI-local tools callable by the model (tui_ask_user_choice, tui_open_selector, etc.) live in app/runtime/client.rs and register via run.start.tools.
Runtime path
Precedence: CODELIA_RUNTIME_CMD / CODELIA_RUNTIME_ARGS (dev override) → bundled runtime in CLI launch context → source checkout default (bun packages/runtime/src/index.ts).
Specs
tui-tea-architecture.md · tui-architecture.md

TUI-specific layer: notification-to-log projection in app/runtime/parser/ (~4,400 non-test lines) is specific to TUI scrollback formatting. Future Desktop clients will need to decide what to share vs render natively.

telemetry (metrics & UI)

core → runtime → protocol → crates/tuiCross-cutting · Always on

TakeawayTelemetry is always active and aggregated solely by runtime. core records raw per-call timing and token usage; runtime emits run.metrics per call, run.summary on run completion, and serves telemetry.get on demand. The TUI displays these totals without recomputing them.

Per LLM call
Provider and model (including served model), latency & TTFT, output TPS, tokens (reasoning, image, cache read/create), cache hit/miss/unknown & rate, cost_usd with source (api_list / unavailable), retry count & wait, and context window utilization
Aggregates
TelemetrySummary: call count, token breakdown, cache hit/miss/unknown counts, cost, retries, tool execution & wait times, compaction count/duration, per-model breakdown — tracked for both the current run and full session (surviving Agent rebuilds)
Runtime health
Startup and assembly phase timings, process memory, active subagents, and RPC backpressure metrics inside telemetry.get.runtime
TUI health
Zero-allocation ring buffers tracking frame render, stream flush, and wrap-cache timings alongside TUI + runtime RSS
Invariant
Every new provider or transport must verify normalized usage and timing through buildRunMetrics across reasoning and tool turns (runtime/tests/provider-metrics.test.ts); missing metrics stay unavailable rather than clearing prior TPS or context state.
Spec
llm-call-diagnostics.md
