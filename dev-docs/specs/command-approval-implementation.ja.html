サンドボックスと
コマンド承認の実装設計

「ファイルを直してテストして」と頼むと、Codelia は編集対象を確かめ、テストを起動してよいかを判断する。起動後は OS がテストとその子孫の書き込み・通信を制限する。まず何が保護されるかとOS ごとにその保護が成立する条件を見てから、承認と起動の流れを追う。コードから読みたい場合はテストと write の実装へ。

実行アーキテクチャ

ローカルの隔離コマンドは、Codelia runtime で起動を承認し、共通の Rust ヘルパーから MXC に渡す設計とする。明示的に full-access を選んだ場合も runtime が承認を扱い、起動後のシェルはログインユーザーの権限で動く。

サンドボックスが決めること

ファイル・通信・ホスト IPC の実効範囲。隔離下のテストが別プログラムを起動しても、子プロセスには同じ境界が適用される。

承認が決めること

指定された条件で今回の操作を開始できるか。Auto approve が許可したテストにも同じ書き込み範囲と通信制限が適用される。

サンドボックスは何を守るか

workspace-write では、通常ファイルをログインユーザーの権限内で広く読める。ワークスペース直下のソースと .env.local は、未設定ならどちらも読み書きできる。.git/config は読めるが変更はできない。特定のファイルを隠すには、利用者がそのパスを非公開に指定する。設定例 · 他のエージェントとの比較

シェルに与える権限の上限

起動モード 読み取り 書き込み 直接通信
readonly ツリー外の通常ファイルも可 専用の一時領域 遮断
workspace-write 同上 作業ツリーと専用の一時領域 遮断
full-access ログインユーザーの権限 ログインユーザーの権限 ホストと同じ

workspace-write でも、閉じた標準入力で調査だけを行う要求には investigation を使い、作業ツリーへの書き込みを与えない。プロジェクトのコードを動かすテストには development を使う。起動時のプローブや MCP サービス用の隔離シェルは調査プロファイルに留める。要求ごとの選択条件

開発用シェルから見えるもの

対象許される操作と、その理由
ソース、生成物、外部の SDK通常ファイルの読み取りは作業ツリーの外にも及ぶ。ツールチェーンやライブラリを使うため。ツリー内の通常の編集はホストへ即時反映され、テストが失敗しても途中の変更は残る。ツリー外の通常ファイルは既定で読み取りのみ。
Git 管理データgit status や差分の取得に必要なので読める。設定に含まれる remote URL も見える。設定、hooks、refs などの管理パスには書けない。linked worktree では .git が指す実際の管理ディレクトリと共通ディレクトリまで解決する。
プロジェクトの .codelia/エージェントは設定を読める。設定の保存はユーザー操作を受けた隔離外の runtime が行う。利用者が同じ場所を非公開に指定した場合は、読み取りも制限する。
ユーザーが非公開に指定したパス隔離時にユーザーまたは SDK ホストが指定したファイル・ディレクトリは読み書きを制限する。指定のない ~/.ssh や ~/.aws などは OS の通常の読み取り権限に従う。ワークスペースの外側では、通常どおり書き込み範囲の制限が効く。
Codelia の認証・権限設定Codelia が保存したファイルも通常の読み取り規則に従う。ユーザーが読めるファイルに保存されたトークンは、非公開指定がなければ隔離シェルからも読める。権限や認証設定をエージェントが改変できないよう、書き込みは独立して保護する。
通信・ホスト上のサービス隔離したシェルと子孫の直接通信を遮断する。ホストの Unix ソケットや名前付きパイプにはプラットフォームごとの検証が要る。Auto approve の問い合わせは隔離外の runtime から送る。リモート MCP のツール実行は、そのサーバーの権限に従う。

非公開パスと OS ポリシーの適用 Git 管理領域の解決 プロジェクト設定の保護

コマンドの検索には Codelia を起動した環境の PATH を渡す。SDK ホストは shellPath で指定できる。インストール先が異なる Bun や Cargo も、起動元の PATH にあれば名前で検索できる。macOS・Linux の隔離シェルは HOME とキャッシュに専用の一時領域を使うため、各ツールの設定や依存キャッシュまで引き継ぐわけではない。コマンド検索と保存ルールの照合

パス名だけでは決められないケース

ホームディレクトリから起動したら、設定はどうなるか

ホームそのものを作業場所にしても、ユーザー所有の正規の保存先で検証できた projects.json から、サンドボックスモードと非公開パスを適用する。たとえばホーム用の readonly と非公開ディレクトリの指定は両方とも有効になる。この重なりを認めるのは読み込み時だけで、同じ場所へのモード変更は管理画面から保存できない。

.codelia/ 配下への直接書き込みはディレクトリ全体で制限する。設定の別名を調べる際には runtime が読む config.json の参照先を照合するため、過去のセッションや worktree が多くても、それらを一件ずつ走査する必要はない。ホーム起動の回帰テスト

二つの名前が同じファイルを指す

シンボリックリンクは参照先のパスをたどれる。ハードリンクでは二つの名前が同じファイル実体を指す。信頼したツリーの通常ファイルはその実体を編集できるため、ツリー外に以前からある別名にも変更が見える。非公開に指定された対象には、共有された実体も検査する。macOS では保護対象の別名を排除できない場合、開発シェルを起動する前に止める。

例外は標準 macOS 開発シェルで認めた Git オブジェクトの既存共有。clone のテストを動かせる一方、組み込みの書き込みは対象が Git 管理データの別名なら拒否する。元リポジトリと clone の関係図

保護するファイルがまだない、または名前の表記が違う

未作成の .codelia/ も、ユーザーが後で設定を保存できるように名前を予約する。組み込みツールは既存項目をデバイス番号と inode で照合し、未作成で大文字・小文字などが違う候補は、親ディレクトリで別名と判定できるかを調べる。区別が確かめられない場合は保護を優先する。macOS のシェルでは保護ディレクトリを支える親の削除・移動も制限する。Linux で未作成の名前を保護する条件は次節のとおり。

名前と実体の照合 Seatbelt の親ディレクトリ保護

承認の後で対象が変わった、または保護を強制できない

たとえば新規作成を承認したファイルが、実行前にエディターから作られた場合、組み込みツールは作成先を再照合して停止する。シェルも起動直前に要求とバックエンド能力を再照合する。必要な隔離が使えなければ sandbox_unavailable で起動を止める。OS 隔離を外すには、ユーザーが full-access を選ぶ必要がある。

未作成の対象の照合 起動直前の確認

同じ保護を OS ごとにどう強制するか

MXC は共通の起動 API を提供する。ソースをライブ編集しながら秘密ファイルやホストのサービスを保護できるかは、その OS のバックエンドとホスト構成によって決まる。

macOS ｜ パスに権限を与え、既存の別名を確認する

製品の既定は直接 Seatbelt。arm64 では CODELIA_MAC_SHELL_BACKEND=mxc で MXC も選べる。同じプロファイルを適用する理由の一つがホスト IPC で、評価時には MXC の標準設定で作業ツリー内のホスト Unix ソケットに接続できた。Codelia の専用設定ではこの接続と TCP loopback の遮断を確認した。

実機では通常の共有 clone・pack 済み clone・linked worktree のすべてで、ファイルを生成する Bun テストが両経路で成功。非公開に指定されたパスの別名を調べる索引は 4,096 エントリが上限で、超えると隔離シェルが使えない場合がある。MXC の既定化には異常終了時の子孫回収の検証も残る。

テストランナーが同じサンドボックス内で起動した子には終了シグナルを送れる。ユーザー名の解決には Open Directory の libinfo サービスだけを許可する。macOS 26.2 arm64 の直接 Seatbelt・MXC で、子の終了と whoami・Node の os.userInfo() を確認した。同じ環境の OS 付属 /bin/ps は、子の PID を指定しても起動時に EPERM となる。

Linux ｜ 書ける親の中に、まだない秘密ファイルを置く場合

利用者がこのファイルを非公開に指定した例を考える。想定する操作は「エージェントがソースを編集している間に、ホスト側のエディターが .env.local を作る」。作業ツリーは双方から編集でき、後から生まれた秘密ファイルの内容は子プロセスにも見えないことが条件になる。

実行方式この条件で起きること
製品の rootless gVisor保護対象に空のファイルやディレクトリを重ね、ホストのソケット・FIFO とネットワークを制限する。既存の親マスクで覆えず、保護用マウント先がまだなければ起動前に拒否する。そのバックエンドに依存する組み込みの新規作成も影響を受ける。
評価中の MXC / bubblewraparm64 VM では既存ファイルのライブ編集は成功。書ける作業ツリー直下の未作成名を隠す設定では、起動のためにホストにその名前が作られ、正常終了後も残った。私有 overlay にすると今度はワーカーの編集が原本に届かない。
MXC ＋ AppArmor の試験管理者がポリシーを導入した VM では、起動による保護名の作成は発生せず、ホストが後から作ったファイルは子孫から読めなかった。通常ファイルの編集は双方向に反映。製品への統合と、実ホストでのポリシー・別名の検証が残る。

Windows ｜ ホストに既にあるアクセス権を含めて評価する

候補の ProcessContainer では、ホストが ALL_APPLICATION_PACKAGES などに与えた ACL（アクセス制御リスト）が実効権限に影響する。名前付きパイプにも独自の ACL があるため、外部通信を拒否する設定だけでローカルサービスへの接続可否を決められない。

Windows 11 ARM の CI では最小のコンソールプログラムが起動したが、Node は DLL 初期化時に 0xC0000142 で終了した。Server 2025 x64 は必要な能力を提供しなかった。通常のツール実行・ACL・IPC・子孫回収をまとめて確認できた標準の隔離構成はまだない。

共通ヘルパーの配布と各 OS の受け入れ試験

macOS arm64 のヘルパーは公式 Rust SDK を使い、Bun・Node から呼び出せる。SDK ホストでは createMacMxcShellBackend() をアダプターに指定できる。

  1. 共通ヘルパーの契約を確定する。 一回の要求、実行ファイルと引数、作業ディレクトリ、実効権限を渡す。開始受付・起動失敗・終了結果を別々に返し、制御用の通信とコマンドの標準入出力を分ける。macOS arm64 のヘルパーで実装済み。
  2. 配布から通常の起動までつなぐ。 CLI の OS・CPU 別パッケージに macOS arm64 のヘルパーとライセンスを同梱し、runtime 単独インストールでも解決できるようにした。ホストごとの能力確認を通してから起動する。
  3. 同じ受け入れ試験を各 OS で通す。 ツリー外読み取り、ライブ編集、保護対象、直接通信とホスト IPC、子・孫の継承、取消、異常終了を検証する。Windows の既存 ACL など OS 固有の項目を加える。
  4. 確認できた構成から切り替える。 UI・承認・保存ルールの挙動を再確認し、利用できない隔離モードには原因を表示する。

コマンド承認のシーケンス

人に確認する条件

判定順 条件 結果
入口で拒否 所有者不一致、未登録、明示 deny、権限上限超過、必要な隔離を強制できない。 確認前に終了。起動 0 回。
人に確認 ホストの上限内で、追加の書き込み先などの権限が必要。 人に一回確認。完全解析必須のホストでは解析不能を拒否。
ローカルで許可 組み込みの読み取り・状態照会、または実行条件が一致した保存ルール。 モデルを呼ばずに実行。
隔離内の親シェル 未登録のテストやビルドも対象。現在の隔離内に収まり、強制ルールを評価できる。 Auto approve が有効ならローカルで一度起動する。明示確認で許可ルールがなければ人に確認する。

有限ループの例

for f in a.txt b.txt; do wc -l "$f"; done

解析時は二つのファイルをそれぞれ照合する。両方が調査用ルールに収まれば、元のシェルを一回起動し、保存ルールは増えない。パイプや分岐もプログラム全体に判定を返す。関数、コマンド置換、未対応の方言などは内容を確定できない要求として扱う。

同じディレクトリで何度も使う cargo test や npm run build は、実行ファイルと引数列を固定できるときに、人がセッションまたはプロジェクトに保存できる。実行前に cwd・実行ファイル・権限を再照合する。確認画面で任意の後続引数を許可すると、同じ実行条件の cargo test --release も通る。以前の完全一致ルールは元の範囲を保つ。プロジェクト内のテスト内容は後から変わり得る。

シェル以外のツールは、どこで権限を確かめるか
  • apply_patch の dry_run は作業ツリー内の読み取り権限でプレビューできる。保護付きの適用で、先の操作が空ける予定の場所へ移動するパッチは、最初の変更前に拒否する。
  • image_export は元の画像を読み出した後、書き込む直前にも許可された出力先を照合する。
  • ローカル stdio MCP と CLI の mcp test は同じ起動経路を使う。設定した環境変数の値は専用の入力パイプでサービスに渡し、起動引数や確認画面には載せない。
  • 進捗表示など、ネイティブ TUI に登録された五つの UI 操作は通常の起動確認を省く。一般のクライアントツールには、その登録に対する承認ポリシーが適用される。

Auto approve はいつ人に聞くか

強制ルールを評価でき、現在の隔離内に収まる起動はローカルで決める。追加の書き込み先が必要な場合はホスト上限内の範囲を人に示す。明示確認で単純なコマンドを許可するときは、次回にも使うルールを保存できる。

追加の権限申請をモデルで審査するのは後続段階。許可の根拠、失効と再申請の条件は権限モデルにまとめている。

設計本文・受け入れ条件

Auto approve のモデルと待ち時間

ローカル TUI の /auto-approve で Enable in this workspace を選ぶと、その作業場所で隔離内の自動起動が有効になる。Follow と Custom は、この作業場所を有効にすると同時にモデルの経路を選ぶ。Follow は実行中のチャットの組み込み provider に追従し、Custom は登録済みの組み合わせを固定する。既存の認証を使い、追加のキーやセッションごとの送信確認は不要。

SDK がモデル審査を委任した場合

通常の run ではユーザーの依頼、/goal の自動継続では保存された目標を使う。適用済みの Steer、コマンドと引数、cwd、書き込みと通信の実効範囲を合わせて判断する。添付本体、無関係な履歴や環境変数の値は除外する。

待ち時間を生む経路

審査対象に決まってから判断材料を作る。独立した検索・状態照会は審査待ちと並行できる。固定の5秒期限、審査件数枠、専用予算は設けていない。

同じ依頼でも実効権限で扱いが変わる。有効にした作業場所の workspace-write 内でテストが完結すれば、runtime が一度起動する。full-access で任意のプロジェクトスクリプトを起動する要求は人に確認する。

登録表 審査に渡す情報

テストと write をコードで追う

macOS のローカル TUI で「失敗するテストを直して、もう一度実行して」と頼んだ例。作業場所はローカル clone、設定は workspace-write と Auto approve。テストはシェルでプログラムを起動し、テストファイルの修正には組み込みの write を使う。

テストを起動するまで

  1. 何を起動するかを固定する。 親エージェントの shell から createShellAuthorizer に、元のプログラム、cwd、stdin が入る。bun test ./development.test.ts はプロジェクトのコードを動かすので、書き込みを伴える開発プロファイルになる。解析結果は判定に使い、コマンドを断片に分けて順に実行することはない。 shell-approval.ts
  2. その場所で OS が守れる範囲を確かめる。 workspacePathProtection が Git 管理領域、プロジェクトの .codelia、非公開パスをまとめる。バックエンドがこの要求を強制できなければ sandbox_unavailable。この段階で止まったテストには、審査モデルを呼んでも起動権限を与えられない。 shell-backend.ts
  3. 今回の起動を許可するか決める。 routeApproval が拒否ルール、権限の上限、付与済みの範囲や保存ルールを照合する。この例はローカルの親エージェントによる隔離内の起動なので、confined_auto_launch で即時許可する。追加の書き込み許可が要る場合は人に確認する。 route.ts · dispatch.ts
  4. 同じ要求を一度だけ起動する。 許可が届いたあと、起動直前に要求と実行条件を再照合し、consume で許可を消費してから backend.launch に渡す。直接 Seatbelt と MXC のどちらでも制限を受けるのは Bun とその子孫。テストの途中までに作ったファイルは作業ツリーに残る。 shell ツール · プロセスの管理

なぜ Git オブジェクトを共有した clone でもテストできるのか

起動時にどこまで走査するか

ローカル TUI の標準 macOS バックエンドで、追加の書き込み先がない開発シェルに適用する。Git の管理データを読み、対応する objects ディレクトリの実体を照合できたときに、その中の再帰走査を省く。認証・権限ストアや個別の保護パスとの重なりは先に判定する。Git の config・hooks・refs と、別のオブジェクトストアを指す alternates 設定も保護する。ほかの保護ディレクトリの同期走査は残る。

Git 管理領域の解決 別名の検査 共有 clone の実機テスト

同じ依頼で write を使うとどうなるか

組み込みツールでは操作とファイル名が最初から分かる。runtime は選んだ対象を照合し、ファイルの有無によって実行方法を変える。付与済み範囲の通常の書き込みでは審査モデルへの往復は発生しない。

既存のテストを修正

writeSelectedFile は withSelectedFile で対象を開き、実体と保護条件を再照合する。Git 管理データの別名なら拒否する。通常ファイルは同じ実体に書き込んでから長さをそろえるため、既存の別名にも変更が見える。途中失敗で一部の変更が残り得る。

新しいテストを作成

対象が未作成なら、選んだ親ディレクトリと作成先が今も同じ条件かを確認し、createDirectoryMutationBroker が固定の作成操作を起動する。macOS ではその操作に必要な場所だけに書き込みを許す。作成先に別ファイルが先に現れたら失敗する。

write の入口と内容ハッシュ 対象の再照合と既存ファイル更新 新規作成・移動・削除

テストが走らなかったとき、どこから調べるか
sandbox_unavailable
バックエンドが今回のプロファイルを強制できない。OS ごとの対応状況、要求された保護パスと Git 管理領域を確認する。
review_evidence_unavailable / review_unavailable
前者は判断材料を安全に用意できなかった場合、後者は審査先から使える判定が得られなかった場合。隔離下の親シェルでは未実行の理由がエージェントに戻る。
approval_expired
要求の取り消しや承認条件の変更が起きた。起動直前の照合と許可の消費を確認する。
起動後にテストが失敗
終了コードと標準エラーを調べる。テスト自身の失敗も、実行中に OS がファイル操作を拒否した場合もある。途中までに作成したファイルは残り得る。

再送・取り消し・子孫の回収

「許可が出た」「プロセスが起動した」「操作が完了した」は別々の状態。シェルで一部を実行した後に失敗しても、同じ操作を自動で再実行しない。

時点 現行の処理 MXC 導入時に引き継ぐ条件
確認・審査を待機中 同じ所有者・要求 ID・内容の再送は進行中の処理に合流する。取り消し・意図や権限の変更後に返った許可は使えない。 ヘルパーへ渡す前に最新の状態を検査し、失効した要求の起動を 0 回にする。
起動直前 実行元・シェル原文または直接 argv・cwd・実効権限に束縛した許可を一度消費する。 開始受付とコマンド完了を区別する。起動に失敗しても別のバックエンドで勝手に再実行しない。
実行中 実行器が stdin、stdout、stderr、終了コード、シグナルを管理。停止はプロセスグループまたは子ハンドルに通知し、必要時に強制終了する。 runtime からの入力終了・出力・中止をワーカーに伝搬し、孫も含む停止を各 OS で観測する。
切断・異常終了 ライブ実行の変更は残り得る。受付やキャンセル応答だけでは外部操作の結果や全子孫の終了は確定しない。 macOS の Node ヘルパー試作では親パイプ切断時の回収が成功したが、ヘルパーを強制終了すると子孫が生存した。製品の Rust ヘルパーは SDK の終了報告を確認する。ワーカー異常終了などで回収の証跡が欠けた場合は、回収未確認を返す。

デスクトップからの変更

クライアントは initialize の supports_sandbox_mode_management を確認する。sandbox.get は次の run の実効値・設定元、現在適用中の agent／run の値、編集可否と理由、選択肢を返す。

sandbox.set({scope:"project", mode:"workspace-write"}) はユーザー操作としてアイドル時に保存する。成功時はキャッシュ済みエージェントを無効化し、次の run に反映。実行中や CLI 固定時には理由付きで拒否する。runtime RPC は実装済み。デスクトップのチップ描画と全体既定の変更 RPC はこの改修の対象外。

旧設定からの移行と影響

対象 改修した仕組み 利用者・呼び出し元への影響
モード 旧権限モードをサンドボックス設定に変換。起動前の承認は別に選ぶ。 既定は workspace-write と明示確認。新設定で full-access を明示すると OS 隔離が外れる。
シェルの許可 コマンド文字列の分割・prefix 許可を、プログラム全体の解析と一回の許可に置換。 有限ループの for / do / done は構文として扱う。禁止された段がある場合、どの段も開始しない。
許可リスト 旧 deny と手書き allow を引き継ぐ。共有 allow は旧 trusted の範囲、または利用者が /permissions trust で信頼したプロジェクトで有効。/permissions untrust で取り消せる。 たとえば旧 command: "cargo test" は cargo test --release にも適用される。cargo build や複合プログラムは別に判断する。
ツールの入口 登録したツールの実体・所有者・効果を照合。親・子・直接 RPC の呼び出しに適用。 読み取りや状態照会は通常ローカル判定で進む。子は親から委任された範囲内で実行する。
実行基盤 現在は OS 別に隔離を起動する。MXC 採用後は共通ヘルパーがこの処理を引き受ける。 不足する隔離能力は起動前に通知する。自動で full-access に切り替える経路は設けない。
「今後も許可」はどこに保存されるか
  • チームの手書き設定はリポジトリの .codelia/config.json にある permissions.allow。旧 trusted または明示したプロジェクト信頼を条件に使用する。
  • 自分だけがこのプロジェクトで許可したツールはユーザーの projects.json に保存する。他の開発者や他のプロジェクトには適用しない。
  • 確認画面で保存したシェルルールはセッション内、またはユーザー設定ディレクトリの launch-approvals/ に保存する。画面に示した実行ファイル、引数の範囲、cwd、実効権限で照合する。

TUI の /permissions list で状態を確認できる。

旧設定が残るワークスペース

旧設定 解決後のサンドボックス 移行後の挙動
minimal readonly ツリー外の通常ファイルも読める。作業ツリーへの書き込みは制限する。
trusted workspace-write 信頼した作業ツリーにライブ編集でき、既存の共有 allow も有効になる。認証・権限設定への書き込みと直接通信を制限する。
full-access workspace-write 起動時に移行を案内する。隔離解除には、新しい --sandbox-mode full-access などでの明示指定が必要。

CLI → 環境変数 → プロジェクト個別設定 → 全体既定の順に解決し、同じ層では新しい指定が優先する。たとえば全体が旧 minimal、プロジェクトが旧 trusted なら workspace-write。さらに CLI で readonly を指定すると、その起動では readonly が優先される。
