CODELIA · SANDBOX & COMMAND APPROVAL

Sandbox & Command Approval Implementation

When you ask Codelia to “fix this file and run the tests,” the runtime checks what the command touches, decides whether startup is admitted, and lets the OS confine writes and network access for the shell and every child it spawns.

  1. Sandbox = access ceilingControls which files, local IPC, and network sockets a running command and its descendants can reach.
  2. Approval = launch gateControls whether the runtime may start this invocation under that mode. Both axes are independent.
  3. Single launch pathConfined shells check policy, bind effective authority, re-verify before launch, and consume a single grant.

Execution architecture

Confined local shell commands are admitted in the Codelia runtime and dispatched through OS backends — Seatbelt on macOS (or MXC opt-in), the packaged MXC Bubblewrap helper on Linux (or rootless gVisor fallback), and MXC ProcessContainer under qualification on Windows. Choosing explicit full-access or an approved one-shot escalation still routes through runtime admission, then runs the shell unconfined as the login user.

What the sandbox decides

Effective access to files, direct network connections, and host IPC. Even if a sandboxed test spawns compilers or worker subprocesses, descendants inherit the same boundary.

What approval decides

Whether runtime may start this invocation under the requested conditions. Commands admitted by Auto approve still run under the same write roots and network blocks.

What the sandbox protects

In workspace-write, ordinary user-readable files are readable broadly within the login account's OS permissions. Workspace source files and an un-protected .env.local inside the workspace are writable, while .git/config stays read-only. To hide specific files or directories from both reads and writes, mark them in protected_paths. Settings & examples · Comparison with other local agents (Japanese)

Cases where paths alone are not enough

Launching from the user's home directory

Even if the workspace is ~ itself, verified user-owned projects.json resolves both the sandbox mode and protected paths (for instance, readonly for home combined with private directories), while keeping ~/.* top-level dot-entries and ~/Library read-only. Alias checks against runtime-owned config.json inspect only canonical config targets rather than crawling session logs or old worktrees. Home-workspace regression test

Two names pointing to the same file

Symlinks resolve through their targets; hard links share the same inode. Because an in-place edit to an ordinary workspace file modifies its underlying inode, a pre-existing hard link outside the workspace sees that update. Protected targets check hard-link aliases as well: on macOS, if a protected path's alias cannot be isolated cleanly, launching a development shell is blocked upfront.

The deliberate exception is shared Git objects inside standard macOS development shells so shared clones can run tests, while built-in file tools still reject writes targeting Git metadata aliases. See the shared-clone diagram below

Absent protected files or case-insensitive names

Even if .codelia/ or a private config does not exist yet, its name is reserved so later user config writes stay safe. Built-in file tools verify existing files by device + inode and check parent directories when targets are absent or differ in casing, erring on protection when ambiguous. On macOS, confined shells also prevent moving or deleting parent directories anchoring protected paths.

Targets changed after approval, or isolation cannot be enforced

If an approved file creation races with an external editor creating that path before dispatch, built-in tools re-verify and abort before writing. Confined shells likewise re-check backend capability immediately before launch and fail with sandbox_unavailable if enforcement cannot hold; disabling OS isolation always requires explicit full-access or an approved one-shot escalation.

OS enforcement and limits

MXC provides a shared launch helper API, while effective confinement for live workspace edits combined with protected paths depends on each OS backend and host kernel configuration.

macOS · Path grants and pre-existing alias checks

Default execution uses direct Seatbelt; on arm64, CODELIA_MAC_SHELL_BACKEND=mxc selects the packaged Rust MXC helper. Both apply Codelia's custom profile blocking host workspace Unix sockets and TCP loopback (whereas upstream MXC's stock profile permitted host workspace Unix sockets during evaluation).

Tests creating files across shared clones, packed clones, and linked worktrees pass on both Seatbelt and MXC paths. Alias indexing caps at 4,096 entries per protected directory; exceeding that cap may block development-shell launches rather than weakening protection. Full descendant reaping on abnormal helper crashes remains under tracking before considering MXC as macOS default.

Child processes spawned inside the sandbox can signal their own descendants, and username lookup permits Open Directory libinfo services (whoami and Node os.userInfo() succeed on macOS 26.2 arm64 under both Seatbelt and MXC; stock /bin/ps returns EPERM even for child PIDs).

Linux · Absent protected secrets inside writable trees

Consider a protected file such as .env.local inside a writable workspace when a user creates it from an editor while a confined agent run is active: source edits must propagate live, yet the newly created secret must stay invisible to confined processes.

BackendBehavior for absent protected paths
Packaged MXC / Bubblewrap (default on x64 & arm64)Runs unprivileged user/network/PID namespaces, seccomp, and private /tmp + /run with bwrap >= 0.5.0. Overlays empty files/dirs onto existing protected entries, while masking absent names in a writable workspace requires either parent masking or an OS policy layer (private overlays would block live source edits).
Rootless gVisor fallback (CODELIA_LINUX_SHELL_BACKEND=gvisor)Overmounts empty files/dirs and blocks pathname Unix sockets (--host-uds=none), FIFOs, and direct network. Windows · Evaluating pre-existing host ACLs

In MXC ProcessContainer evaluation, existing host ACLs granted to principals like ALL_APPLICATION_PACKAGES affect effective access, and named pipes carry their own ACLs independent of network blocks. On Windows 11 ARM CI, a minimal console binary launched cleanly while Node exited with 0xC0000142 at DLL init; Server 2025 x64 lacked the required host capabilities. No default confined Windows host configuration is qualified yet.

Packaging the common helper and per-OS acceptance gates

The macOS arm64 / Linux helper binds Microsoft's official Rust MXC SDK and is invocable from both Bun and Node (createMacMxcShellBackend() is available to SDK hosts).

  1. Freeze the helper IPC contract. Pass one request with executable, args, cwd, and effective authority; distinguish launch ack, startup failure, and exit result while separating control messages from child stdio.
  2. Ship binaries cleanly. Bundle the platform helper and license inside per-OS/arch CLI packages while resolving standalone runtime installs too; verify host capabilities before every launch.
  3. Pass shared acceptance tests per OS. Cover outside-tree reads, live workspace writes, protected entries, network/IPC blocks, descendant inheritance, cancellation, and crash reaping alongside OS-specific gates (like Windows ACL checks).
  4. Promote only after qualification. Keep sandbox_unavailable explicit whenever a host lacks required isolation; never downgrade silently to full-access.

Out of scope for local confinement

Cloud gVisor workers, destination-scoped HTTP/egress proxies, and selective snapshot diff rollback belong to future phases. SDK hosts can already supply additional approvalProtectedPaths.

Finite shell loop example

for f in a.txt b.txt; do wc -l "$f"; done

Static analysis resolves both a.txt and b.txt across the finite loop. When both satisfy investigation rules, runtime starts the original shell once without writing extra rules. Pipelines and conditionals are evaluated as one whole program; shell functions, command substitutions, and unsupported dialects count as opaque and require fallback treatment.

Commands run repeatedly in the same directory (like cargo test or npm run build) can be saved per session or per project when executable + args match cleanly. Re-execution re-checks cwd, binary, and authority. Choosing trailing-arg wildcard allows e.g. cargo test --release under the same conditions, while legacy exact rules stay exact.

How non-shell tools check authority
  • apply_patch --dry_run needs only workspace read access; full guarded patches reject moves into paths vacated by an earlier hunk before touching disk.
  • image_export verifies output destination permissions right before writing, even after reading the source image.
  • Local stdio MCP servers and CLI mcp test share one launch path, passing configured secret env values over an input pipe rather than CLI args or confirmation prompts.
  • Five registered native TUI client UI tools (such as selectors and user-choice prompts) skip command confirmation, while general client tools follow their registration approval policy.

When confirmation asks a human

Commands whose full program passes mandatory rules and stays within the current sandbox resolve locally. Requests requiring extra write roots or unsandboxed escalation route to Auto Review (when eligible) or prompt the user once. Under explicit confirmation, simple bound commands can also propose reusable rules.

Grant rules, authority expiration, and re-prompt triggers are documented further in permission-model.md.

Spec body & acceptance gates

Auto approve models and latency

Selecting Enable in this workspace under /auto-approve enables confined launches for that workspace. Follow chat provider follows the active built-in chat provider, while Custom model pins a registered provider/model pair using existing credentials with no extra per-session transmission prompt.

Delegated reviewer evidence

Includes the accepted user input (or active /goal objective), applied Steers, command + args, cwd, and effective write/network scope. Raw attachments, unrelated history, and secret env values are excluded before dispatch.

Latency characteristics

Evidence is assembled only once a request routes to review. Independent reads/status checks can proceed concurrently while awaiting review. No artificial 5 s cutoff, per-run quota cap, or separate dollar budget is imposed.

Code walkthrough: test launch and write

Consider running in the local macOS TUI inside a clone with workspace-write and Auto approve enabled when asked to fix and re-run a failing test: shell runs the test runner while built-in write fixes the test file.

Launching the test command

  1. Bind the exact invocation. The parent agent's shell call passes the raw program, cwd, and stdin mode into createShellAuthorizer. bun test ./development.test.ts runs project code, selecting the development profile rather than fragmenting the program for piece-by-piece execution. shell-approval.ts
  2. Resolve OS-enforceable protection. workspacePathProtection combines Git protected metadata, project .codelia/, Codelia credentials, and configured private paths. If the backend cannot enforce that set, launch fails immediately with sandbox_unavailable — reviewer models cannot override missing sandbox protection. shell-backend.ts
  3. Route admission. routeApproval checks deny rules, ceilings, saved allowances, and workspace confinement. Because this is a confined parent shell under workspace Auto approve, it resolves directly via confined_auto_launch without prompting. Extra write roots route to Auto Review or human confirmation. route.ts · dispatch.ts
  4. Re-verify and launch once. Right before execution, runtime re-verifies the request against live state, calls consume on the single-use grant, and passes the invocation to backend.launch. Bun and any subprocesses share the confined sandbox, leaving any edited test files live in the workspace. shell.ts · shell-executor.ts

Why clones with shared Git objects still run tests

How much does macOS startup scan?

For standard macOS development shells without extra write roots, runtime inspects Git metadata to locate the linked objects directory and skips recursively walking the object store, while checking credentials, config files, Git protected entries (config, hooks, refs, alternates), and explicit protected_paths aliases synchronously. git-metadata.ts · protected-aliases.ts · Shared-clone Seatbelt test

Using built-in write in the same task

For built-in file tools, operation and target path are explicit upfront. Runtime checks the exact file identity and dispatches differently depending on whether the target already exists; normal writes inside an approved workspace need no reviewer model call.

Editing an existing test

writeSelectedFile opens the target via withSelectedFile, re-verifies inode identity and protected-path rules, rejects Git metadata aliases, and truncates/writes in place — so pre-existing external hard links stay consistent.

Creating a new test file

When absent, runtime re-verifies the parent directory and target name and invokes createDirectoryMutationBroker, scoping macOS write allowances tightly to that path and failing if a racing file appears first.

Evidence could not be assembled safely, or the reviewer model failed/timed out; the agent receives the structured refusal reason without fallback execution.

Retries, cancellation, and descendant reaping

“Admitted,” “spawned,” and “completed” are separate lifecycle states. A command that fails after partial execution is never replayed automatically.

PhaseCurrent runtime handlingMXC helper contract requirement
Waiting for prompt / reviewIdentical retries from the same caller/ID/payload coalesce onto the active request; decisions invalidated by cancel, Steer, or authority changes are dropped before use.Re-check live state right before handing off to the helper so expired requests cause 0 spawns.
Just before launchConsume one single-use grant bound to caller, raw shell or argv, cwd, and effective authority.Separate spawn ack from command completion; never fall back to another backend after a spawn failure.
While runningExecutor manages stdin, stdout, stderr, exit status, and signals; cancellation signals the process group or child handle and escalates if needed.Propagate stdin close, streams, and cancellation cleanly and confirm descendant termination per OS.
Disconnect / crashLive edits remain on disk; cancelling or dropping an RPC channel does not undo external side effects or guarantee descendant death.Unlike early Node prototypes where killing the helper left grandchildren alive, the Rust MXC helper verifies SDK termination status and reports unconfirmed reaping if the worker died unexpectedly.

Where remembered permissions are stored
  • Shared team allowances live under permissions.allow in repo .codelia/config.json and apply when legacy-trusted or explicitly trusted via /permissions trust.
  • Personal tool allowances (like webfetch) live in user-owned projects.json under remembered_tool_allows without affecting teammates or other projects.
  • Interactive shell rules persist in the session or under user state launch-approvals/, bound to executable, arg matching, cwd, and effective authority.
