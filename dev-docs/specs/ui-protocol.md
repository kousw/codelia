# UI Protocol Spec（Core ⇄ TUI/Desktop）

This document covers the Rust UI (TUI/future Desktop) and the TypeScript side execution runtime (core + tools).
Defines a **bidirectional protocol** to be used between.

Premise:
- `AgentEvent` of `packages/core/src/types/events/*` is a “domain event” generated by **core's runStream**.
- To connect with UI, `AgentEvent` alone is not enough, **envelope (IPC) + UI→core input + core→UI request** is required.

This specification assumes `packages/protocol` is the canonical source.

Implemented image extension (2026-09-13): `supports_image_generation` advertises
the optional `image.model.get`, `image.model.configure`, and `image.artifact.get`
methods (`packages/protocol/src/image.ts`). `image.model.get` returns requested
mode, effective availability and a safe message; availability is not account or
price verification. Configure with empty params uses existing UI pick/confirm
requests; explicit params supply mode/provider/model/endpoint/api_key_env. Writes
are idle-only and enabled modes require confirmation. Cancellation preserves the
old configuration. Chat selection/credentials are unchanged. Artifact get accepts
only a workspace-scoped artifact ID and returns validated metadata plus a bounded
inline PNG data URL, not a runtime-host path. The TUI matches the response ID and
artifact identity before previewing; normal tool/run requests are not sent by
these commands. Unsupported embedding environments reject image operations.
See [image generation section 1.1](image-generation.md#11-implemented-public-api-slice).

---

## 0. Purpose / Non-purpose

the purpose:
- Make the UI and execution runtime **loosely coupled** (enabling TUI/GUI replacement)
- Ensure compatibility (version/capabilities) and extensibility (namespacing)
- Support cases that require intervention from the UI, such as “selection/confirmation/input”

Non-purpose:
- Delegate “UI internal operations (key input/focus movement)” to core (UI is owned by UI)
- Provider-native payload transport (the optional preview below carries normalized text only).

---

## 1. Role (Actor)

- **UI**: Rust TUI (in the future, Desktop UI will also use the same protocol)
- **Runtime**: TS side process (including core + tools). From the UI’s perspective, it’s a “server”

> The current `packages/core` is a library, so it does not speak the protocol by itself.
> Runtime protocol server is implemented in `packages/runtime`, and TUI/Desktop connect to it over stdio JSON-RPC.

---

## 2. Transport

### 2.1 Recommended: stdio

- UI spawns Runtime and communicates bidirectionally with `stdin/stdout`
- **stdout is for protocol only**, logs are output to **stderr** (prevents stdout pollution)

### 2.2 Message framing（v0）

v0 adopts **NDJSON (JSON Lines)**:
- 1 row = 1 JSON object
- UTF-8
- Each message ends with `\n`

future:
- If you need a large payload or strict boundaries, move to length-prefix (negotiate with version of `initialize`)

---

## 3. Wire Envelope

This protocol adopts a form compatible with JSON-RPC 2.0 (for ease of implementation and correlation).

```ts
export type RpcId = string;

export type RpcRequest = {
  jsonrpc: "2.0";
  id: RpcId;
  method: string;
  params?: unknown;
};

export type RpcResponse = {
  jsonrpc: "2.0";
  id: RpcId;
  result?: unknown;
  error?: { code: number; message: string; data?: unknown };
};

export type RpcNotification = {
  jsonrpc: "2.0";
  method: string;
  params?: unknown;
};

export type RpcMessage = RpcRequest | RpcResponse | RpcNotification;
```

Design policy:
- Request/response requires **correlation id** (needs to wait with UI confirm etc.)
- notification is fire-and-forget (without `id`)
- `params` **allows future expansion** (does not discard unknown/extra fields)

## 5. Run model (“one run”)

The chat UI is usually ``one user utterance = one agent execution.''
This one time is called `run`.

### 5.1 `run.start` (required)

UI → Runtime request。

params (example):
```ts
export type RunStartParams = {
  input: { type: "text"; text: string };
  session_id?: string; // optional resume target
  force_compaction?: boolean; // optional one-shot compaction run
  tools?: ClientToolDefinition[]; // optional per-run client-provided tools
  tool_choice?: "auto" | "required" | "none" | string; // optional per-run tool choice
  ui_context?: UiContextSnapshot; // Optional: current active file / selection etc.
  meta?: Record<string, unknown>;
};
```

result (example):
```ts
export type RunStartResult = {
  run_id: string;
  session_id?: string; // normal runs return it; optional for older clients/compaction compatibility
};
```

The dedicated child runtime persists its new session before returning both ids.

`session_id` in request params remains an optional **resume target**. Creating a
new session uses an omitted request `session_id`; runtime creates the id and
returns it in `RunStartResult`. An unknown caller-supplied resume id continues to
fail with `SESSION_NOT_FOUND` rather than implicitly creating a session. This
lets a subagent parent persist the real child-created session id without
overloading resume semantics.

The process-backed subagent bootstrap manifest is an internal runtime launch
contract, not a new public UI protocol method. Normal child communication starts
with `initialize` only after the child has validated that manifest and installed
its delegated permission boundary. The private `subagent.request` bridge carries
authenticated send/receive/list and parent-authorized edit/write/shell requests.
It is not exposed as a public UI RPC. Parent models use `task_send_message` and
`task_receive_messages`; incoming context uses the existing hidden user message
event. Model `task_wait` wakes on unread messages; public `task.wait` retains its
existing wait semantics.

Subagent spawn requires parent-chosen `name` (an agent display name) and accepts
optional `label` (the work assignment). There is no automatic name allocation.
Names must be unique within the owner session across completed tasks as well. Task summaries expose `name`,
backed by `subagent.name`; existing nameless records remain compatible. Task
operations still address `task_id`. Peer messages expose optional runtime-derived
`sender_name` / `recipient_name` alongside their authoritative UUID addresses.

Subagent spawn also accepts optional `profile` or `model` (mutually exclusive).
`model` requires `name` and optionally accepts `provider`, `reasoning`, `verbosity`,
and `fast`; an omitted provider uses the parent provider. An explicit selection
wins over `subagent.default_profile`; with neither selected nor configured, the
complete parent model settings are inherited. Profile configuration is documented
in `subagent-collaboration.md`. No model/auth availability probe is performed.

#### Client-provided tools

External runtime clients may pass request-scoped custom tools in
`run.start.params.tools`. Runtime maps each client tool to the same core `Tool`
surface used by built-in and MCP tools, exposes its definition to the model for
that run, and proxies execution back to the connected client.

```ts
export type ClientToolDefinition = {
  type?: "function";
  name: string;
  description: string;
  parameters: Record<string, unknown>; // JSON Schema object
  strict?: boolean;
  timeout_ms?: number;
  approval?: "default" | "never";
};
```

Names must be unique for the run and must not conflict with runtime-provided
tools. Client tools are intended for host-app-owned capabilities such as
read-only evidence inspection, recent-log reads, or app-specific action
preparation. The client remains responsible for local approval UX and execution
policy for those capabilities. Before proxying a client tool, runtime requires
a trusted registration and applies runtime permission checks. The
`approval` field is accepted for wire compatibility and grants no authority.

When the model calls a client-provided tool, Runtime sends a JSON-RPC request to
the client:

```ts
method: "client.tool.call"

export type ClientToolCallRequestParams = {
  run_id: string;
  name: string;
  arguments?: Record<string, unknown>;
  raw_arguments: string;
};

export type ClientToolCallResult =
  | { ok: true; result?: string | { type: "text"; text: string } | { type: "json"; value: unknown } | { type: "parts"; parts: unknown[] } }
  | { ok: false; error: string };
```

Runtime converts successful results into normal tool output and continues the
agent loop. Failed results are returned to the model as tool errors.

If a client tool does not respond before its configured `timeout_ms`, Runtime
sends a cancellation notification before rejecting and removing the pending
request:

```ts
method: "client.tool.cancel"

export type ClientToolCancelParams = {
  request_id: string; // id of the earlier client.tool.call request
  run_id: string;
  name: string;
  reason: "timeout";
};
```

The client must dismiss only interaction state that is still tracked under the
matching `request_id`; stale notifications must not close a different active
dialog. A response sent after cancellation is no longer matched by Runtime and
is ignored as an orphan response.

Client tool results may return multimodal content via
`{ type: "parts", parts }`, using the same `ContentPart[]` shape as core tool
results. Image parts should be returned as `image_url` parts with an inline
data URL, for example:

```json
{
  "type": "image_url",
  "image_url": {
    "url": "data:image/png;base64,...",
    "media_type": "image/png",
    "detail": "high"
  }
}
```

Use data URLs because provider-side model calls cannot read local client file
paths. Keep image payloads small: base64 expands the payload, and tool results
may be stored in session/history records. Prefer resizing/compressing
screenshots before returning them, and reserve future blob/artifact references
for large or repeated images.

To add a new client-provided tool:

1. Define a `ClientToolDefinition` in the client that sends `run.start`.
   For the TUI this is `crates/tui/src/app/runtime/client.rs`.
2. Use a unique, client-scoped name. Avoid names that look like runtime
   built-ins unless the tool really has runtime-owned behavior.
3. Make the `description` model-facing and self-sufficient. It should say what
   the tool does, when to prefer it over chat text or runtime tools, and any
   important limits such as read-only behavior, no returned selection, update
   keys, or sentinel ids.
4. Put non-obvious parameter semantics in each schema field description. This
   includes defaults, fallback labels, special return ids, units, bounds, and
   whether a field is only display text.
5. Implement the `client.tool.call` handler on the client side and return one
   of the supported result shapes: plain text, `{ type: "text" }`,
   `{ type: "json" }`, or `{ type: "parts" }`. For image parts, use inline
   base64 data URLs and keep payloads bounded. Use `{ ok: false, error }` for
   user cancellation, unsupported arguments, or local execution failures.
6. Leave runtime permission decisions to the trusted tool registration.
7. Keep benchmark/headless paths independent of UI-only tools. The TUI disables
   its injected client tools when `CODELIA_BENCHMARK_MODE=1`.
8. Add focused tests for schema injection, disabled benchmark behavior, client
   handler behavior, and any state cleanup such as clearing tracked progress
   rows after `/clear`.

The TUI uses this mechanism to expose TUI-owned interaction/display tools on
each run: `tui_ask_user_choice`, `tui_open_selector`,
`tui_preview_artifact`, `tui_focus_context`, and `tui_show_progress`. These
tools manage TUI-local display/interaction state. Runtime-owned work should
stay on runtime tools or direct runtime RPCs. Benchmark/headless execution must not depend on these
UI-only tools; the TUI skips injecting them when
`CODELIA_BENCHMARK_MODE=1`, and `CODELIA_TUI_CLIENT_TOOLS=0` can disable them
for local runs.

TUI client tool definitions must be self-sufficient for model use: the
top-level description should say when to prefer the tool over chat text, and
parameter descriptions should document sentinel return ids, update keys, and
non-obvious display behavior.

| Tool | When to use | Result behavior |
| --- | --- | --- |
| `tui_ask_user_choice` | Ask the user to pick exactly one follow-up question, suggestion, or next action. Prefer this over rendering numbered lists in chat when the next step depends on a user choice. Each primary choice requires a unique non-empty `id` and non-empty `label`; malformed, duplicate, reserved, or unknown fields fail the call instead of being silently omitted. | Opens the TUI pick dialog and returns `{ selected_id }`. `allow_none` appends `__none_of_these__`; `allow_other` appends `__other__`. `message` is shown above the choices. The TUI supplies a 15-minute timeout because this is a blocking human-input tool; `client.tool.cancel` clears its matching dialog and pending id when that deadline expires. |
| `tui_open_selector` | Show scan-and-compare rows, such as candidate files, sessions, or tools, when the user does not need to answer immediately. | Opens a read-only list panel and returns a short success text; it does not return a selected row. |
| `tui_preview_artifact` | Show substantial text, markdown, JSON, or diff content without cluttering the chat log. | Opens a read-only preview panel and returns a short success text. Large content should be summarized before preview. |
| `tui_focus_context` | Move the visible log focus after producing or inspecting context. | Moves to `bottom`, `top`, `latest_error`, or `latest_tool_call`, and returns whether the focus target was found. |
| `tui_show_progress` | Show progress updates without writing repeated progress messages in chat. | Updates one graphical progress row by `id`, or by `phase` when `id` is absent. In inline mode, once a row is committed to immutable terminal scrollback, the next update is appended as a new row. Live call/result transcript lines are suppressed on success; errors remain visible. During history replay, successful call/result pairs reconstruct the progress row without issuing client RPCs. `status: "completed" | "error"` releases the row so later reuse starts fresh. |

### 5.2 `agent.event` (required)

Runtime → UI notification. Carry `AgentEvent`.

params (example):
```ts
export type AgentEventNotify = {
  run_id: string;
  seq: number;              // 0..N（ordering）
  event: AgentEvent;        // packages/core/src/types/events
  meta?: Record<string, unknown> & { replayed?: boolean };
};
```

> Since `AgentEvent` itself is a core “display event”, it is fine as long as the UI draws it directly.

Events sent by `session.history` carry `meta.replayed: true` so clients can
restore display-only state without repeating client-tool actions. The TUI also
recognizes unmarked replay from older runtimes while a history request is
pending, excluding events for the active run. Truncation can omit a matching
call or result, in which case no progress row is reconstructed for that pair.

`llm.status` is an informational display event for OpenAI verification
recommendations or buffering wait state. It may arrive before LLM completion;
it does not become assistant history or authorize automatic retry/model switching.
The TUI uses fixed strings for known states and ignores unknown/clear states.
> However, for future expansion, wire has `seq` and `meta` on the envelope side.

### TUI live transcript (`Implemented`)

The TUI advertises `supports_text_delta` and consumes the existing incremental
delta protocol documented below. It adds no separate model/provider callback or
stream lifecycle wire event. The first chunk of each `stream_id` starts local
display tracking; canonical output, retry and terminal status close that tracking.

- TUI projects live reasoning and assistant segments into the normal transcript
  using the same Markdown, indentation, highlighting, wrapping, scroll and
  selection paths as canonical output. There is no separate preview panel or
  Thinking/Responding header. Scrolling up preserves the reading position while
  new output grows; resizing rewraps the full response.
- TUI maintains live body rows in its display log and updates them in place.
  Completed lines can enter native inline scrollback during generation. A long
  paragraph without newlines can also commit complete graphemes before the last
  unfinished grapheme or unmatched inline Markdown marker. An unfinished code
  line remains mutable until newline/channel completion. Thus earlier generated
  output is available through native terminal scrolling before `final`.
- Runtime batches can contain many token events; parse/highlight once per draw,
  canonical handoff or reset. Native insertion and its scheduling both stop at the
  stable source position, preserving the mutable tail and avoiding redraw loops.
  Keep partial-line anchors reusable even if a pending suffix temporarily empties.
- On canonical events, confirm already-rendered matching segments instead of
  appending duplicate text. The display remains visible during awaited archival writes. Corrections to an uncommitted tail update it in place;
  corrections to immutable native history append an explicit corrected response.
  Retry/cancel drops tracking but preserves observed attempt text, followed by
  the existing retry/run status. Log reset clears all local display rows.
- Streamed final responses do not append a duration row or extra trailing spacer
  that would push the body upward. Elapsed time appears in the existing run status
  line after completion. Legacy canonical-only display retains its existing log
  duration behavior.

Additional notes (`text` and `final`):
- `final` is an event that indicates "this turn is completed" and also has a body text.
- `text` is a complete body event for one assistant text block of a non-terminal model step.
- The UI does not depend on both `text` and `final` coming (there are cases where the body comes only with `final`).

Incremental deltas (`text.delta` / `reasoning.delta`, opt-in):
```ts
type TextDeltaEvent = { type: "text.delta"; delta: string; stream_id: string; index: number };
type ReasoningDeltaEvent = { type: "reasoning.delta"; delta: string; stream_id: string; index: number };
```
- Sent only when the client declared `ui_capabilities.supports_text_delta: true`
  in `initialize`. Without it (CLI, headless, subagent child runs) the
  event stream is unchanged and providers receive no delta sink.
- Provisional and ephemeral: deltas are not written to the session log and are
  never replayed by `session.history`. The complete `text` / `reasoning` /
  `final` events stay authoritative.
- Identity: `stream_id` identifies one model call attempt. `index` groups the
  provisional blocks of one kind inside that stream: blocks are numbered per
  kind from 0 in the order their first delta arrives, and concatenating every
  delta of one (`stream_id`, kind, `index`) gives the text streamed for that
  block. `index` is for provisional display only. It does **not** identify a
  complete event: complete events may contain blocks that had no deltas (for
  example Anthropic `redacted_thinking`, hosted-tool placeholders) or text that
  was not streamed (initial content in a Google `step.start`), so a client must
  not match provisional blocks to complete events by `index`.
- Lifecycle of one `stream_id`, which clients rely on instead of `index`:
  - All of its deltas arrive before any later `agent.event` other than
    `text.delta`, `reasoning.delta` and `llm.status`; after such an event no
    delta of that `stream_id` follows.
  - `llm.retry` after it: the attempt failed; discard its provisional text. The
    next attempt uses a new `stream_id`.
  - The step's complete events (`reasoning`, `text`, `tool_call`, `final`, …):
    replace all provisional text of the `stream_id` with them. A terminal step
    sends only `final` (its body is the step's text blocks joined by `\n`).
  - The run ends without them (`run.status` error / cancelled): discard it.
- Inside one OpenAI call that falls back from websocket to HTTP (or
  reconnects), the `stream_id` stays the same and further deltas are suppressed
  once some were emitted; the complete events still arrive.
- Coalescing: runtime merges consecutive deltas with the same key and flushes
  them every ~40 ms and always before any other `agent.event` of the run, so
  ordering relative to `tool_call` / `text` / `final` is preserved. `seq`
  stays contiguous across deltas and other events.
- Cancel / abort / error: pending (not yet flushed) deltas are dropped, never
  flushed; nothing is sent after `run.cancel` is accepted.
- Providers: OpenAI Responses (HTTP + websocket), named Responses endpoints
  (incl. DeepSeek), OpenRouter, xAI, Anthropic, Google, Moonshot and Z.ai emit
  text deltas. Reasoning deltas come from Responses reasoning summary (or
  reasoning text) events (OpenAI, named endpoints when the endpoint streams a
  summary, OpenRouter, xAI), Anthropic `thinking_delta`, Google
  `thought_summary` and Moonshot/Z.ai `reasoning_content`. Text that a provider
  delivers outside delta events (e.g. initial content in a Google `step.start`)
  is not streamed; a step with no deltas is valid.

See `dev-docs/specs/run-visibility.md` for UI rendering guidelines based on these events.

### 5.3 `run.cancel` (recommended)

UI → Runtime request。

params (example):
```ts
export type RunCancelParams = { run_id: string; reason?: string };
```

result (example):
```ts
export type RunCancelResult = {
  ok: boolean;
  status?: "running" | "completed" | "error" | "cancelled";
};
```

Runtime should treat run.cancel as best-effort and idempotent.
If the run is active, it must attempt to stop LLM calls and tool execution and
then emit `run.status` with `status: "cancelled"`.
If the run already completed, Runtime may return `ok: false` or `status: "completed"`.
After a cancelled status, no further agent events should be emitted for that run.

### 5.3.1 `run.steer` (optional)

UI → Runtime request (advertised by `server_capabilities.supports_run_steer`). Injects a user steer message into the active `run_id` at the next safe agent boundary (before the next model step or immediately before `final`), without aborting in-flight model or tool calls and without breaking `tool_call`/`tool_result` pairing.

params:
```ts
export type RunSteerParams = {
  run_id: string;
  input: RunInput;
  client_steer_id?: string;
};
```

result:
```ts
export type RunSteerResult = {
  ok: true;
  steer_id: string;
};
```

Notes:
- Returns `-32002` (`RUN_NOT_FOUND`) when `run_id` is not the active run (including if the run already finished before arrival), or `-32602` for empty/invalid input.
- Compaction runs (`force_compaction: true`) do not consume steers.
- Applied steers emit an `agent.event` `{ type: "steer_applied", steer_id, content, timestamp }` and are persisted in session history as real user messages.
- Any steers remaining unconsumed when the run ends (including cancelled/error runs) are drained into `run.status.unconsumed_steer_ids` so the UI can return them to its local queue in chronological order. See `dev-docs/specs/tui-run-steer.md`.

### 5.4 `session.list` (recommended)

UI → Runtime request. Get the session list for Resume.

params (example):
```ts
export type SessionListParams = {
  limit?: number; // default: 50
  scope?: "current_workspace" | "all"; // default: "current_workspace"
  workspace_root?: string; // optional explicit filter target
  include_archived?: boolean; // default false
};
```

result (example):
```ts
export type SessionListResult = {
  current_workspace_root?: string;
  sessions: Array<{
    session_id: string;
    updated_at: string;
    run_id?: string;
    message_count?: number;
    last_user_message?: string;
    workspace_root?: string;
    pinned?: boolean;
    archived_at?: string;
  }>;
};
```

Notes:
- `scope: "current_workspace"` is the default and filters by exact worktree/workspace match.
- Lane sessions are treated as worktree-local sessions; sibling lane worktrees are not flattened into the default resume list.
- Use `scope: "all"` when the UI intentionally wants a cross-workspace picker or legacy unscoped sessions.
- `current_workspace_root` can be returned so the UI can show the exact current scope when presenting the picker.

### 5.4.1 `session.update` (implemented)

Advertised by `supports_session_lifecycle` only when the session store supports
lifecycle updates. Params are `{session_id, pinned?: boolean, archived?: boolean}`;
at least one boolean must be supplied. Result is `{session: SessionStateSummary}`.
Pinning prevents automatic compression/diagnostic expiry. Archive hides a session
from the default list and makes unpinned run events eligible for gzip archival with
diagnostic snapshot removal, including legacy gzip. Explicit dumps may expire. Original messages, active context, index
and references remain intact. Explicit resume unarchives the session. Archive of the
current runtime's active session is rejected; other active writers are skipped by
cleanup. `include_archived: true` lists archived sessions for resume/unarchive.
Hosts without lifecycle support reject the operation without local disk fallback.

### 5.5 `session.history` (recommended)

UI → Runtime request. Play the session history (agent.event).

params (example):
```ts
export type SessionHistoryParams = {
```

### 5.5.1 `session.open` (recommended)

UI → Runtime request. Bind the runtime to an existing session before its next run, without starting one. Advertised by `server_capabilities.supports_session_open`.

```ts
export type SessionOpenParams = { session_id: string };
export type SessionOpenResult = { session_id: string };
```

- Clients that resume a session should send `session.open` when the session is opened (for example alongside `session.history`), so a session-scope `model.set` sent before the first message is saved to that session instead of being replaced by its saved override on the first `run.start`. Runtime runs a `model.set` received after a `session.open` only once that open has finished, so clients may send `model.set` without waiting for the open response.
- Runtime loads the session, applies its saved `codelia_model_override`, and drops the current Agent so the next `run.start` (with or without `session_id`) restores that session's history. It does not replay events; use `session.history` for that.
- Opening the session the runtime is already bound to is a no-op that keeps the live Agent. Opening another session switches to it.
- Errors: `-32602` without `session_id` or for a delegated (subagent) session, `-32004` session not found, `-32005` session load failed, `-32001` while a run is active. On error the runtime stays bound as before. Runtime orders `session.open` with `run.start` admission.
- Runtimes without the method answer `-32601`; clients may ignore that and rely on the first `run.start` to bind.

### 5.16 Auth management (`auth.status` / `auth.login*`, optional)

UI → Runtime requests for clients that own their sign-in UI (desktop GUI).
Gated by `server_capabilities.supports_auth_management`, which is true only
when runtime owns credentials (`auth.model = "runtime-default"`); host-owned
auth rejects the family with `-32602 "auth is host-owned"`. These are user
actions over RPC, not model tools.

`auth.status { provider? }` → `{ providers: AuthProviderStatus[], pending_login? }`:
```ts
type AuthProviderStatus = {
  provider: string;
  kind: "builtin" | "config";            // config = providers.<id> endpoint
  methods: Array<"api_key" | "oauth" | "device_code">;
  saved: { method: "api_key" | "oauth"; expires_at?: number } | null;
  env: { name: string; present: boolean } | null; // never the value
  active: boolean;                        // provider of the current model
};
```
Never returns key or token material. Allowed during a run.

`auth.login`:
```ts
type AuthLoginParams =
  | { provider: string; method: "api_key"; api_key: string }
  | { provider: string; method: "oauth"; callback?: "loopback" | "paste"; open_browser?: boolean }
  | { provider: string; method: "device_code"; open_browser?: boolean };
type AuthLoginResult =
  | { status: "completed"; provider: string; method: "api_key" }
  | { status: "pending"; login_id: string; provider: string; method: "oauth" | "device_code";
      auth_url?: string; verification_url?: string; user_code?: string };
```
- Rejected with `-32001` while a run is active. `methods` from `auth.status`
  lists what each provider accepts (OpenAI: oauth/device_code/api_key; others
  and `providers.*` endpoints: api_key).
- `api_key` must be a non-empty single-line string (≤ 4096 chars, trimmed). It
  is saved to the local auth file (reload-then-merge; other providers kept)
  without network validation and is never logged.
- `oauth` / `device_code` return `pending` as soon as the URL/code exists; one
  pending login per runtime (a second gets `-32001`). `open_browser` defaults to
  false (the client opens the URL). `callback: "loopback"` (default) uses the
  localhost callback server; `paste` requires `auth.login.complete`.
- Completion is reported once by the `auth.login.status` notification:
  `{ login_id, provider, method, status: "completed" | "failed" | "cancelled", message? }`
  (`message` is a bounded, token-free reason).
- `auth.login.complete { login_id, callback_input }` → `{ ok: true }` accepts the
  redirected URL or `code=...&state=...`. Unparseable input or a state mismatch
  returns `-32602` and keeps the login pending.
- `auth.login.cancel { login_id }` → `{ cancelled: boolean }` stops the callback
  server or device-code polling and emits `status: "cancelled"`.
  The pending slot is reserved before the session is created (its `login_id`
  is visible in `auth.status`); cancelling during that setup makes the
  original `auth.login` fail with `-32003`.
- A successful login invalidates the cached agent when the provider is the
  current one (or supplies cached credentials); if a run started meanwhile the
  invalidation waits for that run to finish. The session is kept.
- `ui_capabilities.supports_auth_management` suppresses the `initialize`-time
  onboarding pick; lazy prompts at `run.start` remain the fallback.

### 5.17 Config read/write (`config.get` / `config.set`, optional)

UI → Runtime requests behind `server_capabilities.supports_config_rw` (true
only for runtime-owned config files; host or disabled config rejects with
`-32602`). Only registry keys are exposed — scalar leaves whose layers merge as
"last wins" (`packages/runtime/src/config-keys.ts`). Permission rules,
`providers.*`, `mcp.*`, startup-check commands and API-key env names are never
exposed. Model and theme keys are read-only here (`write_via: "model.set"` /
`"theme.set"`).

```ts
type ConfigEntry = {
  key: string;                         // e.g. "search.mode"
  value: string | number | boolean | null; // effective value
  source: "default" | "global" | "project";
  global?: string | number | boolean;  // raw value in the global file
  project?: string | number | boolean; // raw value in the project file
  type: "boolean" | "integer" | "string" | "enum";
  enum?: Array<string | number | boolean>; min?: number; max?: number;
  default_scope: "global" | "project"; // CONFIG_GROUP_DEFAULT_WRITE_SCOPE
  writable: boolean; write_via?: string;
};
```

- `config.get { keys? }` → `{ paths: { global, project | null }, entries, errors? }`.
  Precedence is registry defaults < global < project. The project file is
  `<workspace root>/.codelia/config.json`, the same root the agent reads
  (`workspace.root` / sandbox root / runtime working dir). An unparseable
  layer is reported in `errors` (no file contents) and treated as empty.
  Allowed during a run.
- `config.set { scope, key, value? , unset? }` → `{ key, scope, path, entry, applies: "next_run" }`.
  `scope` is required; there is no implicit target resolution. `value` is
  validated against the key's type/range; `unset: true` removes the leaf and
  prunes emptied parents. Unrelated raw JSON is preserved.
- Reflection: config files are re-read on every resolve, but the agent snapshots
  model/tools/search/skills/subagent/permissions when it is built. A successful
  write therefore drops the cached agent; the next `run.start` rebuilds it and
  restores the session history. `config.set` is rejected with `-32001` while a
  run is active so a run never changes mid-flight; running subagents keep their
  snapshot.

### 5.18 Approval rules (`permissions.list` / `permissions.remove`, optional)

UI → Runtime requests behind `server_capabilities.supports_permissions_rw`
(runtime-owned config only). Config-file rules come from the `permissions.allow` / `deny` lists in global and project configuration (see [permission settings](../../docs/reference/config.md#permissions)). Their identity consists of `tool` / `command` / `command_glob` /
`skill_name`.

```ts
type PermissionRuleEntry = {
  kind: "allow" | "deny";
  scope: "global" | "project" | "system";   // system = built-in allowlist
  rule: { tool: string; command?: string; command_glob?: string; skill_name?: string };
  removable: boolean;                       // false for system
};
```

- `permissions.list { include_system? }` →
  returns the effective `sandbox_mode` (value, source, optional legacy input), the optional legacy `approval_mode` for display, and the rules, paths, and read errors. Local `initialize` also reports `sandbox_mode`. When a native Windows confined shell is unavailable because no configuration has qualified, `initialize.shell_sandbox_issue` is `windows_native_unqualified`. Clients can explain this independently of the requested mode. File rules are listed by layer; `include_system` includes immediate built-in tool registrations.
- `permissions.remove { scope, kind, rule }` → `{ scope, kind, path, removed }`
  removes every structurally equal entry from that one file's list (a
  narrower rule never matches a broader one); emptied lists/objects are pruned.
  `removed: 0` writes nothing. Rejected with `-32001` during a run. A removal
  drops the cached agent so the next run uses the updated policy.
- The optional `launch_rules` list contains shell approvals for this workspace. Each entry has an opaque `id`, a session or project scope, and a format identifier. For `exact-argv/v2`, display the executable, arguments, working directory, origin and profile. Preserve the original command word and source when supplied. For `argv-prefix/v1`, show the required words and the fact that any trailing arguments match. Older Bun rules keep their original limited targets and can be listed and revoked.
- Local clients can inspect `project_allow_trust` in `permissions.list`. It contains the canonical workspace, effective `trusted`, current `rules`, and an opaque `revision`. With `supports_project_allow_trust`, an idle user can call `permissions.projectTrust.set({workspace, trusted, expected_revision})` after reviewing the entries and the scope of future edits. The response echoes the workspace and effective decision. A stale revision or changed workspace requires a fresh list. A busy runtime rejects the write.
- `permissions.list.remembered_tools` contains user-owned tool-only approvals for this workspace. Send `permissions.remove {scope: "project", remembered_tool: "webfetch"}` to revoke the specified personal entry. Shared config trust and shared file rules are independent.
- To revoke one saved launch rule, send `permissions.remove { launch_rule_id, scope }`. The result echoes the ID and scope and reports the number removed. Creation goes through an eligible shell request and the human confirmation dialog.
- Removing a `deny` rule loosens policy; clients should confirm with the user.
  Workspace sandbox changes use §5.23.

### 5.19 Context usage (`context.usage` / `run.context.usage`, optional)

`server_capabilities.supports_context_usage` advertises both. The shared shape
is `ContextUsage` from `@codelia/shared-types`:

```ts
type ContextUsage = {
  provider: string | null; model: string | null; // null only before any agent exists
  limit_tokens: number | null;  // maxInputTokens ?? contextWindow
  used_tokens: number | null;   // last provider total_tokens (same basis as run.context)
  input_tokens: number | null;  // last provider input_tokens
  left_percent: number | null;  // equals run.context's context_left_percent
  basis: "provider" | "none";   // none: no model call yet
  breakdown: Array<{
    category: "system" | "tools" | "messages" | "tool_results" | "images";
    tokens: number; count?: number; // count: images only
  }>;
};
```

- `used_tokens` / `input_tokens` / `left_percent` are provider-reported only.
  `breakdown` is an estimate of the agent's current history and tool
  definitions (serialized bytes / 3 per category; images via the model's
  image-token estimate, never from encoded bytes). It is not normalized to
  `used_tokens`; clients should label it as an estimate. `system` counts the
  system prompt even before the first run; `tools` uses the latest call's
  definitions (including per-run client tools).
- `context.usage {}` → `ContextUsage & { session_id? }`. Allowed any time. With
  no built agent it returns `basis: "none"`, null counts and an empty breakdown;
  it never builds an agent or prompts for auth.
- `run.context.usage` (Runtime → UI notification, `ContextUsage & { run_id }`)
  is sent only when the client declared `ui_capabilities.supports_context_usage`:
  once after each completed model call (the first agent event that observes a
  new provider usage) and after `compaction_complete`. It is derived data: not
  written to the session log and not replayed by `session.history`. Without
  the opt-in nothing changes (`run.context` continues as before).

### 5.20 Subagent progress (`TaskSummary.progress` / `task.progress`, optional)

Advertised by `server_capabilities.supports_task_progress` (when subagent
execution is available). The shared shape is `TaskProgress` from
`@codelia/shared-types`:

```ts
type TaskProgress = {
  step: number;              // model calls started so far
  max_steps?: number;
  phase: "model" | "tool" | "compacting" | "finishing";
  current_tool?: { name: string; tool_call_id: string; started_at: string };
  last_tool?: { name: string; status: "ok" | "error"; finished_at: string };
  tool_calls: number;        // tool calls requested so far
  updated_at: string;
};
```

- Only counts, phase and tool names cross to the parent: tool arguments,
  results and model text stay in the child session (readable with
  `session.history { session_id: child_session_id }`). Tool names are capped at
  128 characters.
- The child reports progress at each model request, `tool_call`,
  `tool_result`, compaction start/end and `final`. The parent keeps the latest
  value in memory only (not persisted; children are session-owned) and ignores
  updates after the task is terminal.
- `task.list` / `task.status` / `task.wait` / `task.cancel` / `task.result`
  include `progress` for subagent tasks when known. The model-facing task tools
  are unchanged.
- `task.progress` (Runtime → UI notification) is sent only when the client
  declared `ui_capabilities.supports_task_progress`:
  `{ task_id, name?, state, progress?, usage?, updated_at }`. It is sent on
  every state change immediately and for progress at most every 250 ms per task
  (latest value wins, trailing send). Shell tasks do not emit it. It is only
  sent while the subagent's owner session is the current session (checked at
  every send, including coalesced trailing sends).

With `supports_goals` on both ends, the local TUI manages a session goal
through `goal.get`, `goal.set`, `goal.pause`, `goal.resume` and
`goal.clear`. These are user actions. Runtime offers each automatic start
through `goal.ready` after releasing the previous run. The client gives
queued user work precedence and echoes the offer once in `goal.continue`,
which returns the ordinary run identity. A client that loses the reply
reconciles the continuation ID through `goal.get`. See [Goals](goals.md)
for scope, state transitions, token accounting and failure behavior.


### 5.22 Local approval reviewer (`auto_review.configure`, optional)

`supports_auto_review_configure` advertises user management of the built-in local
reviewer on a POSIX TUI-local runtime. Embedded host reviewers use their own
configuration. This method is an operator action.

- `{ action: "pick" }` (also the default) opens the mode picker. Enable in this workspace
  enables confined launches and keeps the existing reviewer preference. Follow resolves
  a registered reviewer for the actual chat agent's provider. Custom opens
  the registry picker for one pinned route. Follow and Custom set the shared reviewer preference
  and enable confined launches in the current workspace. This requires picker support and an idle runtime. Cancelling keeps the previous settings. Stale
  selections cannot replace newer settings. Existing enabled test-only v1/v2 settings
  require explicit re-selection before sending under the new auth contract.
- `{ action: "status" }` returns `AutoReviewStatus` from `@codelia/protocol`.
  `confined_launch_enabled` and `confined_launch_issue` report the workspace setting independently of the reviewer `state` and `issue`. It also contains the reviewer selection mode, route label, authentication and data
  disclosures where available. Credential contents are never part of the response.
- `{ action: "off" }` disables confined launches in the current workspace and invalidates pending decisions. Pending review traffic is cancelled. Status and
  disabling are allowed during a run.

The workspace choice applies across sessions for the same directory identity. The reviewer preference applies across workspaces. Follow resolves the active provider for each run.

### 5.23 Workspace sandbox menu (`sandbox.get` / `sandbox.set`)

These operator RPCs are advertised by `initialize.server_capabilities.supports_sandbox_mode_management`. They address the workspace attached to the runtime. The client never submits a filesystem path. The menu manages OS isolation. Auto approve selection uses §5.22.

| Read from `sandbox.get {}` | How the desktop uses it |
| --- | --- |
| `effective.value`, `effective.source`, optional `effective.legacy` | Label for the next run and the reason that mode was chosen. Sources include a CLI flag, environment variable, project, default, SDK and built-in fallback. |
| `applied` | Actual mode of the active run or existing agent, tagged `run` or `agent`. Null before either exists. |
| `project.writable`, optional `project.reason` | Enable the workspace menu, or explain the lock. Examples include `cli_override`, `env_override`, `sdk_managed`, `runtime_busy`, `policy_store_unavailable` and `policy_acl_unverified` (Windows policy-file ownership cannot be verified). |
| `choices[]` | Render each entry’s `id`, `label` and `description`. An `unavailable_reason` disables that choice. A selectable mode still checks the host’s actual protections on each shell launch. |

For example, the user's selection of Workspace write submits:

```json
{"method":"sandbox.set","params":{"scope":"project","mode":"workspace-write"}}
```

On success the response has the same shape as `sandbox.get`. The runtime writes the workspace’s project entry, invalidates the cached agent and uses the new policy for the next run. An already running command keeps the OS permissions with which it was launched. For each subsequent shell request from a surviving subagent, the parent runtime applies its current mode subject to the child’s delegated ceiling. A child admitted read-only stays read-only, and child shells are capped at workspace write. A running agent, fixed source, unavailable choice, unsafe policy store or ineffective selection yields an error with a machine-readable reason. The desktop can refresh after rejection. The first version accepts project scope. Global defaults can still be set in the user-owned policy file. [Protocol types](../../packages/protocol/src/permissions.ts) · [Desktop menu behavior](./desktop/context-and-runtime.md#workspace-sandbox-menu)

## 6. UI → Runtime (Input/Context)

### 6.1 `ui.context.update` (recommended)

The “selected/active file” etc. are held by the UI and shared with the Runtime only when necessary.
Do not send raw key events (do not impose UI convenience).

```ts
export type UiContextUpdateParams = {
// Minimum: “Where are you working now?”
  cwd?: string;
  workspace_root?: string;

  active_file?: { path: string; language_id?: string };

  selection?: {
    path: string;
// 0-based. end is recommended to be exclusive.
    range: {
      start: { line: number; column: number };
      end: { line: number; column: number };
    };
// Optional: If the UI can be generated immediately, include it (if not, core will use the read_file tool)
    selected_text?: string;
  };

// For future expansion
  extensions?: Record<string, unknown>;
};
```

`UiContextSnapshot` is an alias for including the “current UI state” in run.start.
```ts
export type UiContextSnapshot = UiContextUpdateParams;
```

Usage:
- push before agent execution (pass “latest” along with `ui_context` of run.start)
- Push every time the selection changes (but debounce if the frequency is high)

## 8. Additional categories that are likely to be needed (in the future)

When developing TUI/desktop as a “coding agent UI” you will likely need:

- **Artifacts**: Handle diff/image/long log with `artifact_id` reference (large capacity countermeasure)
- **Workspace API**: `workspace.list/read/search` for UI to display file tree / preview
- **History API**: Get and export conversation history/tool history
- **Task/ToDo**: `todos.update` etc. that works with planning tools
- **Clipboard**: Handle copy/paste explicitly (useful in TUI)
  - Planned concrete request for remote-runtime mode:
    `ui.clipboard.read` (see `dev-docs/specs/tui-remote-runtime-ssh.md`)
- **Shell execution**: user-initiated direct execution path
  - Implemented concrete request: `shell.exec`
    (see `dev-docs/specs/tui-bang-shell-mode.md`)

These are not required for v0, but keep the method namespace:
- `artifact.*`
- `workspace.*`
- `history.*`
- `todos.*`
- `shell.*`

### 5.13 `shell.exec` (optional)

Executes a UI-origin shell command without starting an agent run.

Request params:

- `command: string` (required)
- `timeout_seconds?: number` (default 120, max 300)
- `cwd?: string` (optional, sandbox-root bounded)

Result fields:

- `command_preview: string`
- `exit_code: number | null`
- `signal?: string | null`
- `stdout: string`
- `stderr: string`
- `truncated: { stdout: boolean; stderr: boolean; combined: boolean }`
- `duration_ms: number`
- `stdout_cache_id?: string`
- `stderr_cache_id?: string`

`stdout/stderr` may contain excerpt text when truncated; cache IDs can be used with `tool_output_cache`.

## Copied-file upload

Servers advertise `supports_attachment_upload` and `attachment_upload_limits`.
The client begins a transfer with a retry key, name, original byte length and
SHA-256, then sends base64 chunks using the acknowledged byte offset. Finish
returns an attachment ID. Start and Steer accept it in an ordered
`{type:"attachment_ref", attachment_id}` input part. The runtime resolves
the ID for the session before admitting the message. The RPC shapes are in
`packages/protocol/src/attachment.ts`. See [pasted images and files](./input-attachments.md).
